# Deployment Guide — Legacy Compatible Avro Converter

> **SUPPORTABILITY NOTICE**
> A custom `value.converter` is not a supported Kafka Connector 4.x configuration path.
> The KC v4 startup validator does not inspect `value.converter`, so the connector will
> start; however, custom converters are not reviewed, tested, or maintained by Snowflake
> Engineering. **Obtain written approval from Snowflake Support or the responsible product
> team before using this converter in any production environment.**

---

## Purpose

`LegacyCompatibleAvroConverter` preserves the legacy `RECORD_CONTENT` JSON document
contract from KC v3/classic Snowpipe when migrating to KC v4/SSv2. It delegates
Confluent-framed Avro deserialization, Schema Registry authentication, TLS, and caching
to Confluent's public `KafkaAvroDeserializer`, then maps the resulting Avro datum to a
standard Java `Map<String, Object>` using legacy union, logical-type, and null semantics
rather than Kafka Connect's intermediate type system.

Key differences from using the standard `AvroConverter` directly:

| Behavior | Standard AvroConverter + KC v4 | This converter |
|---|---|---|
| Simple nullable union `['null','string']` | Unwrapped (identical) | Unwrapped |
| Multi-type union `['null','string','int']` | Branch wrapper: `{"string":"val"}` | Unwrapped: `"val"` |
| Union of named records (e.g. an event `action`) | One key per branch name; inactive branches null; active branch nested one level deeper | Active branch's fields inlined at the union's path; no branch-name key |
| Date logical type | ISO string: `"1970-01-01T00:00:00Z"` | Integer days from epoch: `0` |
| Timestamp-millis | ISO string | Integer epoch milliseconds |
| Decimal | JSON number, with historical Jackson precision limits | Matching JSON number and precision limit |
| Plain bytes | ISO-8859-1-decoded JSON string | Matching JSON string |
| Plain fixed | Array of signed byte integers | Matching integer array |
| NaN and infinities | Quoted JSON strings | Matching quoted strings |
| Tombstone (null record) | KC tombstone | KC tombstone (preserved) |

The union-of-named-records row is the case that breaks path-based downstream SQL: with the
standard converter, `RECORD_CONTENT:action:type` returns NULL because the value has moved to
`RECORD_CONTENT:action:<BranchName>:type`. `NamedRecordUnionCompatibilityTest` pins both the broken
and the corrected shape.

## Required connector configuration

```
connector.class=com.snowflake.kafka.connector.SnowflakeStreamingSinkConnector

value.converter=com.snowflake.labs.kafka.converter.LegacyCompatibleAvroConverter
value.converter.schema.registry.url=https://your-schema-registry:8081
value.converter.basic.auth.credentials.source=USER_INFO
value.converter.basic.auth.user.info=<user>:<password>

# Optional: one fixed Avro reader schema for all values handled by this converter instance
# value.converter.reader.schema={"type":"record","name":"Event","namespace":"com.example","fields":[{"name":"id","type":"string"}]}

# KC v4 migration and compatibility flags
snowflake.enable.schematization=false
snowflake.streaming.validate.compatibility.with.classic=true
snowflake.validation=client_side
snowflake.compatibility.enable.autogenerated.table.name.sanitization=true
snowflake.compatibility.enable.column.identifier.normalization=true
snowflake.streaming.classic.offset.migration=skip
```

`connector.class` changes in v4 — v3's `SnowflakeSinkConnector` is replaced by
`SnowflakeStreamingSinkConnector`. v4 is not a drop-in replacement for a copied v3 configuration.

`snowflake.streaming.validate.compatibility.with.classic=true` is a startup compatibility check,
enabled by default. It fails startup unless `snowflake.validation`,
`snowflake.compatibility.enable.column.identifier.normalization`,
`snowflake.compatibility.enable.autogenerated.table.name.sanitization`,
`snowflake.enable.schematization`, and `snowflake.streaming.classic.offset.migration` are all set
explicitly. Once the migration is settled you may set it to `false` to skip the check on
subsequent restarts.

Two defaults changed in v4 and matter here:

- `snowflake.enable.schematization` defaulted to `false` in v3 and defaults to `true` in v4. It
  must be `false` to keep the `RECORD_CONTENT` VARIANT contract this converter preserves, and the
  validator requires you to state the choice explicitly.
- `snowflake.validation` defaults to `server_side`, which infers column types from the first
  observed record instead of the registry. Set `client_side` for Avro with a Schema Registry;
  otherwise a declared type can be silently downgraded (for example `FLOAT64` inferred as
  `NUMBER(38,0)`, truncating decimals).

For a migration from classic Snowpipe that preserves the connector name and consumer group, keep
`snowflake.streaming.classic.offset.migration=skip`; do not select a Classic channel-offset
migration mode for that path.

`avro.use.logical.type.converters` is force-set to `false` internally by the converter
to retain raw epoch integers for legacy temporal fields. Decimal logical types (BYTES/FIXED)
are mapped to `double` so KC v4 can serialize them as JSON numbers; values requiring more
than ~15 significant digits may lose precision.
Do not set it in the connector configuration.

`reader.schema` is optional. When present, it must be a string containing one complete Avro schema.
The converter parses it during startup and applies it to every non-null value. Reader defaults,
aliases, field projection, and compatible numeric promotion follow normal Avro schema resolution.
Invalid configuration fails startup; incompatible writer schemas fail individual conversions as
`DataException`s and do not fall back to writer-schema-only decoding. Use Kafka Connect's normal
error-tolerance and dead-letter-queue settings if records with incompatible writer schemas may be
encountered.

configured Maven repositories, so no compatibility claim is made for them.

## Plugin directory layout

The converter JAR must reside in the same plugin directory as the Snowflake KC and
Confluent Avro libraries to share a single classloader. Do **not** place it in a separate
plugin directory — that creates an isolated classloader and duplicates Confluent classes.

```
/opt/kafka/plugins/snowflake-kafka-connector/
    snowflake-kafka-connector-4.1.0.jar          # KC fat-jar (existing)
    kafka-connect-avro-converter-7.9.2.jar       # from Confluent ZIP (existing)
    kafka-avro-serializer-7.9.2.jar              # from Confluent ZIP (existing)
    kafka-schema-registry-client-7.9.2.jar       # from Confluent ZIP (existing)
    avro-*.jar                                   # from Confluent ZIP (existing)
    legacy-compatible-avro-converter-1.1.0.jar   # this converter (NEW)
```

### Building the thin converter JAR

```
mvn package -DskipTests
```

Output: `target/legacy-compatible-avro-converter-1.1.0.jar`

### Optional: plugin ZIP for distribution

```
mvn package -P plugin-zip
```

Output: `target/legacy-compatible-avro-converter-1.1.0.zip` (contains the thin
JAR only). Unzip it into the existing Snowflake KC plugin directory as shown above.

## Strimzi deployment — ARM64

Strimzi does not support downloading arbitrary JARs at runtime in production environments.
The standard approach is a custom Kafka Connect image that bundles the plugin directory.

### Custom Docker image (multi-arch, including ARM64)

```
FROM confluentinc/cp-kafka-connect:7.9.2 AS base

# Add Snowflake KC and the compatibility converter to the plugin directory.
# Download URLs are for illustration; pin to verified artifact hashes in production.

RUN mkdir -p /opt/kafka/plugins/snowflake-kafka-connector

# 1. Snowflake KC fat-jar
COPY snowflake-kafka-connector-4.1.0.jar \
     /opt/kafka/plugins/snowflake-kafka-connector/

# 2. Confluent Avro converter jars (already in base image at a different path; symlink
#    or copy to the plugin directory to ensure single classloader visibility).
RUN cp /usr/share/confluent-hub-components/confluentinc-kafka-connect-avro-converter/lib/*.jar \
       /opt/kafka/plugins/snowflake-kafka-connector/ 2>/dev/null || true

# 3. Compatibility converter thin JAR
COPY legacy-compatible-avro-converter-1.1.0.jar \
     /opt/kafka/plugins/snowflake-kafka-connector/
```

Build for ARM64 (Apple Silicon / Graviton):

```
docker buildx build --platform linux/arm64 -t your-registry/kafka-connect-snowflake:1.0 .
```

### KafkaConnect CR (Strimzi)

```yaml
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaConnect
metadata:
  name: snowflake-connect
spec:
  image: your-registry/kafka-connect-snowflake:1.0
  jvmOptions:
    # v4 buffers off-heap via a Rust Snowpipe Streaming SDK. Cap the JVM heap at roughly
    # 50% of the container's memory so the SDK has room; otherwise the pod is OOM-killed
    # even though the JVM itself looks healthy.
    "-Xmx": "4g"
    "-Xms": "4g"
  resources:
    limits:
      memory: 8Gi
    requests:
      memory: 8Gi
  config:
    config.providers: file
    config.providers.file.class: org.apache.kafka.common.config.provider.FileConfigProvider
```

> **Memory sizing.** The v4 connector uses a Rust-based Snowpipe Streaming SDK that allocates
> off-heap (system) memory for buffering. Limit the JVM heap to approximately **50% of available
> memory** — for an 8 GB worker, `-Xmx4g`. This differs from v3 sizing guidance and is a common
> cause of container OOM kills after migration.

### plugin.path note

Strimzi's `KafkaConnect` CR manages the plugin path automatically when using the custom
image approach above. If using a bare Kafka Connect worker (non-Strimzi), ensure
`plugin.path` in `connect-worker.properties` includes the plugin directory:

```
plugin.path=/opt/kafka/plugins
```

## Offset migration

KC v4 handles offset migration automatically when using the same connector name and consumer
group as the v3 deployment. The correct approach depends on your v3 ingestion method.

### Before you start: verify metadata settings

Confirm that `snowflake.metadata.topic`, `snowflake.metadata.offset.and.partition`, and
`snowflake.metadata.createtime` are enabled on the **v3** connector before migrating (they are on
by default). These populate `RECORD_METADATA` with topic, partition, and offset, which is what any
post-migration deduplication depends on. Without them you have no way to dedupe if something goes
wrong.

### Migrating from v3 classic Snowpipe (file-based ingestion)

Set `snowflake.streaming.classic.offset.migration=skip` (already in the required
configuration above). KC v4 inherits offsets from the Kafka consumer group automatically
when deployed with the same connector name.

> **Shut the v3 connector down gracefully.** Raise
> `task.shutdown.graceful.timeout.ms` on the outgoing v3 connector to a large value before
> stopping it. A forceful termination can prevent offsets from being advanced in Kafka, which
> produces **duplicates** after cutover — the same failure mode that motivated this migration.

Safe cutover procedure:

1. Raise `task.shutdown.graceful.timeout.ms` on the v3 connector.
2. Stop the KC v3 connector and wait for all staged files to complete loading. Classic Snowpipe
   stages files before loading them; any file still queued when you stop the connector loads
   asynchronously. Starting v4 before this finishes can land data out of order.
3. Verify no pending files remain (check `COPY_HISTORY` or pipe status).
4. Deploy the KC v4 connector using the **same connector name** and **same consumer group**.
   KC v4 resumes from the committed Kafka consumer group offset.
5. Validate the first batch of records through both the legacy oracle and the compatibility
   converter using the test harness before cutting over downstream queries.

Complete the switchover within `offsets.retention.minutes` (default 7 days) or the consumer group
offsets expire and there is nothing for v4 to inherit.

Done this way, the path introduces neither duplicates nor gaps.

### Intentional Classic channel-offset migration from v3 Snowpipe Streaming (SSv1)

Only when intentionally migrating offsets stored in Classic Snowpipe Streaming channels, set
`snowflake.streaming.classic.offset.migration` to `strict` (fail if SSv1 channels are not found) or
`best_effort` (fall back to Kafka consumer group offsets), and set
`snowflake.streaming.classic.offset.migration.include.connector.name` to match the v3
`snowflake.streaming.channel.name.include.connector.name` setting. Do not use either mode for the
normal same-connector-name/consumer-group migration described above. The same
`offsets.retention.minutes` window applies.

> **Do not** use `auto.offset.reset=earliest` or manual offset resets with
> `kafka-consumer-groups.sh` — these bypass the documented migration path and risk
> duplicates or data gaps.

## Known constraints

- **Schematization**: only `snowflake.enable.schematization=false` is tested. Enabling
  schematization with this converter introduces untested column mapping and schema
  evolution semantics.
- **Sink only**: the converter implements both `toConnectData` and `fromConnectData`, but
  `fromConnectData` delegates to a standard `AvroConverter` and is not independently
  tested for this use case.
- **Fixed `reader.schema` only**: version 1.1.0 supports one inline reader schema per converter
  instance. It does not discover reader schemas by subject or select a different reader schema per
  record.
- **Removed v3 properties**: v4 rejects `snowflake.ingestion.method`, `buffer.flush.time`,
  `buffer.size.bytes`, `buffer.count.records`, `snowflake.streaming.max.client.lag`,
  `snowflake.streaming.channel.name.include.connector.name`, and `provider`, among others.
  Audit the v3 configuration against the current connector documentation and remove what v4 no
  longer accepts rather than copying it forward.
- **Tested version ranges**: only the combinations listed in the version matrix above
  have been exercised. Upgrade any component only after running the full test suite.
